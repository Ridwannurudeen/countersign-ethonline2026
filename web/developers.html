For developers

Four endpoints. One price, quoted before you pay.

Two unpaid reads identify the guard. Two paid writes ask it to decide. Everything below was read from the live service at https://countersign.gudman.xyz on 2026-09-12; the price and identifiers are configuration and can change.

Endpoints

All responses are JSON. The paid endpoints answer 402 until an x402 payment header is present and settled. Any other path is 404.

Route Paid Request Response
GET /guard No — guardPublicKey (DER hex) and guardIdentifier (HCS-14 UAID). Identify the service before paying it.
GET /.well-known/agent.json No — Agent card: uaid, guardPublicKey, both service endpoints, the x402 terms (network, asset, priceTinybars) and tenantCount. It enumerates no tenants or treasuries.
POST /review Yes { tenantId, mandateEnvelope, scheduleId }, exactly those fields outcome of approved with recipientAccountId and amountTinybars, or refused with the failed check as reason; plus scheduleId, mandateDigest, settlementId and mirrorNodeUrl of the HCS verdict message.
POST /countersign Yes { tenantId, mandateEnvelope, transactionBase64 }, exactly those fields On approval, transactionBase64 with the guard's signature added to the unchanged body. Either way outcome, transactionId, transactionDigest, mandateDigest, settlementId, mirrorNodeUrl.

Paying for a review

The 402 body is a standard x402 payment-required document. It names the exact scheme on hedera:testnet, the guard's operational fee account as payTo, the amount in tinybars, and the resource URL. The mandate envelope is parsed and the tenant checked before the 402 is issued, so a malformed request costs nothing.

Pay from an account that holds none of the treasury's keys. The guard decodes the payment payload and refuses, before settlement, any payer that is the treasury, the owner, the agent or the guard itself. 

402 Payment Required                (fields, as the service constructs them)
scheme       exact
network      hedera:testnet
asset        0.0.0                  HBAR
amount       1000000                tinybars, from the agent card on 2026-09-12
payTo        the guard's operational fee account, never the treasury
resource     https://countersign.gudman.xyz/review   or /countersign
description  Countersign schedule review check

The co-signed client signer

On the buyer path the agent does not call /countersign by hand. It plugs createCosignedClientHederaSigner into an ordinary @x402/hedera client, and the treasury becomes the payer of any x402 purchase, with the guard's review in the loop and the owner's key never online. 

import { createCosignedClientHederaSigner } from "./src/cosigned-client-signer.ts";

const signer = createCosignedClientHederaSigner(treasuryAccountId, agentPrivateKey, {
  guardUaid,            // must equal the uaid in the guard's agent card
  guardOrigin,          // the card is fetched from this origin; redirects are refused
  guardPublicKey,       // the returned bytes must carry exactly one signature by this key
  mandateEnvelope,      // owner-signed, single-use
  guardPaymentClient,   // an x402 client that pays the guard's own review fee
});
What it does

Builds the transfer with the treasury as payer and the facilitator's feePayer as transaction ID account, sets a 180-second validity window, freezes and signs with the agent key, then resolves the guard's card and posts the bytes to /countersign, paying the 402 on the way.

What it verifies

The returned transaction list has the same length, every body's bytes are unchanged, and exactly one signature by the configured guard key was added and verifies against the body. Anything else throws.

What a refusal looks like

A CountersignRefusal error carrying the failed invariant. The purchase is never submitted; the review fee has been paid.

How a treasury comes to use the guard

Enrollment is operator-configured. There is no self-enrollment endpoint, and the deployed instance serves one tenant. These are the steps the operator takes; the provisioning script performs the first two.

  1. Create the treasury with the key tree

    An account keyed 1-of[owner, 2-of[agent, guard]], plus a separately keyed fee-payer account. npm run provision-hosted creates all of them on testnet and writes two files: one with only the guard key, for the host, and one with the owner, agent and payer keys, which must not leave the caller.

  2. Enroll the tenant on the guard

    The guard's configuration names each tenant's owner and agent public keys, treasury account and agent account. At startup the guard reads every treasury's key tree from consensus, requires the three keys to be pairwise distinct and the fee destination to be separate from all of them, and refuses to start on any mismatch.

  3. Sign a mandate per transfer

    The owner signs a mandate naming the allowed recipients, cap, asset and validity window with a fresh nonce. Mandates are single-use, so each approval consumes one.

  4. Resolve the guard by identifier, not by directory

    The caller is given COUNTERSIGN_GUARD_ORIGIN and COUNTERSIGN_GUARD_UAID, fetches the agent card from that origin, and refuses unless the UAID matches exactly and the review endpoint shares the origin. The guard is in no directory. An identifier match is not cryptographic proof that the host controls the guard key.

  5. Propose, pay, read the verdict

    The agent publishes a schedule or freezes a payment, the caller pays the review, and the outcome is on the mirror node and the HCS topic whether or not it was the one hoped for.

Run it yourself

The offline suite needs no credentials and makes no network requests. The hosted runs pay the live guard from your machine and need a funded testnet caller. 

git clone https://github.com/Ridwannurudeen/countersign-ethonline2026.git
cd countersign-ethonline2026
npm ci --omit=peer
npm run typecheck
npm test                          # 543 tests, 543 passing on 2026-09-13
python -m pytest python/ -q       # 13 tests, 13 passing on 2026-09-12

npm run hosted-review             # in-policy transfer, expect an approval
npm run hosted-review refused     # out-of-policy recipient, expect a paid refusal
Python buyer preview

python/ holds an unaffiliated preview of a Python x402 client for Hedera exact payments, laid out to mirror the upstream package. It builds, binds and signs the payment transaction; it has not been contributed to or endorsed by the x402 project.

Stack

TypeScript on Node 24 and Hedera native services only: nested key lists, Scheduled Transactions and the Consensus Service through @hiero-ledger/sdk 2.85.0; x402 through @x402/core and @x402/hedera 2.25.0, settled by the Blocky402 facilitator. No smart contracts.
