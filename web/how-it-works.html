How it works

Two keys, one signed policy, and nothing to take on trust.

Three parties hold one key each. The owner signs policy and can always recover. The agent proposes. The guard checks the proposal against the policy and either adds the second signature or does not. The treasury's key tree makes that arrangement a property of the ledger rather than of anyone's code.

Who holds what

The tree lives on the treasury account itself, readable from the mirror node. The three keys must be pairwise distinct; the guard refuses to start otherwise. 

1-of[
  ownerKey,
  2-of[ agentKey, guardKey ]
]
Owner

Signs mandates offline with the same Ed25519 key that sits in the direct branch. Never needs to be online for a review, and can move funds alone at any time. The owner key never leaves the owner's machine.

Agent 0.0.10502367

The autonomous process that wants to spend. It can publish a Scheduled Transaction or freeze an x402 payment with its own signature, and neither goes anywhere until a second key arrives.

Guard 0.0.10502369

The paid reviewer at countersign.gudman.xyz. Its host holds exactly one private key, its own. Holding one key of a 2-of, it cannot spend the treasury, and holding no owner key, it cannot rewrite policy.

The mandate is the policy, signed once

A mandate is a small JSON object, canonicalized with RFC 8785, domain-separated, and signed by the owner. Its SHA-256 digest is 64 hex characters, which fits the 100-byte Hedera memo, so every proposal carries the digest of the policy it claims to satisfy. An agent cannot edit its own policy because it does not hold the key that signed it.

Mandates are single-use. Before approving, the guard atomically reserves the tenant's nonce in a file-backed SQLite database, and only the request that wins the reservation may sign. A replay with the same nonce, or the same nonce bound to a different digest, is refused.

Two paths, and what the guard actually signs on each

Both paths pay the same way and publish the same kind of verdict. They differ in what the agent submits and, importantly, in what the guard's signature covers. The distinction is easy to blur and this page does not.

Schedule path · POST /review Buyer path · POST /countersign
What the agent submits A Hedera Scheduled Transaction it created and signed, identified by ScheduleID. An ordinary x402 TransferTransaction with the treasury as payer, frozen and signed by the agent, sent as base64 bytes.
What the guard resolves ScheduleInfo for that ScheduleID from a consensus node. The request body's own description of the transfer is never used. The submitted bytes themselves, decoded and checked field by field.
What the guard signs A ScheduleID. It submits ScheduleSign, approving the immutable schedule it resolved from consensus. It does not sign the scheduled transaction bytes. The exact bytes it validated. It adds its signature to the transaction and returns it; the caller checks the body is unchanged and exactly one guard signature was added before handing it to the facilitator.
Who submits to the network Hedera executes the schedule once the key tree is satisfied. The x402 facilitator, which also pays the network fee. The treasury is the payer of the amount only.
How a refusal is proved The schedule exists on the mirror node, executed_timestamp is null, the guard prefix is absent from signatures[]. The transaction ID never reaches consensus: the mirror node returns 404. The verdict record on the HCS topic names the failed check.

What the guard requires before it signs

The validator is a pure function over consensus-resolved data. All of the following must hold on the schedule path; any single failure is a refusal, and the failed check is named in the verdict record. Each line maps to a named test in docs/INVARIANTS.md.

Identity

The requested and returned ScheduleID are identical. The creator and the scheduled payer are the expected agent account. The mandate names this guard's treasury, not another.

Binding

The outer schedule memo and the inner transaction memo both equal the mandate digest.

Envelope

No admin key. Does not wait for expiry. Not executed, not deleted. Expires no later than the mandate, to the nanosecond.

Signers

The agent key is present. The guard key is absent.

Versions

The consensus node's protobuf and services major.minor.patch equal the reviewed allowlist, read before and after resolving the schedule.

Body

Exactly one transaction variant, and it is cryptoTransfer. Transaction fee exactly 100,000,000 tinybars. maxCustomFees empty.

Transfer

HBAR only. Exactly two adjustments: the treasury debit and one allowlisted credit, equal and opposite, positive, no greater than the cap. Canonical numeric IDs, isApproval false, no allowance hooks, no fields outside the audited schema.

Payment

The review fee's payer is not the treasury, the owner, the agent or the guard, checked on the decoded payload before settlement. A payload that cannot be decoded is refused, never settled.

Why it fails closed

ScheduleInfo arrives already decoded, and a protobuf decoder silently drops fields it does not know. A guard that approves on the fields it can see would approve a transfer carrying a field it cannot. So the guard pins the exact HAPI protobuf and services versions, reads them from the same node before and after the schedule, and refuses on any difference. A network upgrade makes the guard refuse everything until a person re-reviews the schema and updates the allowlist. That is the intended failure.

The same posture applies to payment: the treasury-identity rule on the x402 payload returns "refuse" on any decoding error, not "allow".
