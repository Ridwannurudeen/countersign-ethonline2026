Limitations

What Countersign does not do, stated where it matters.

Each limit below is real today, and each names what would have to be true for it to stop being one. A page that hides its limits is making a weaker claim about everything else on it.

Fifteen limits, 2026-09-12

  1. Testnet only

    Every account, schedule, payment and verdict is on hedera:testnet. Nothing has been deployed to mainnet and no mainnet HBAR has been at stake.

    Next a mainnet treasury, a mainnet facilitator, and a re-review of the pinned network versions against mainnet.

  2. No users

    evidence.json records 10 schedule-path reviews, 5 approved and 5 refused, every one with origin operator and zero external. The buyer path has 2 operator runs. These are reliability exercises, not adoption, and the testnet fees paid are protocol trials, not revenue.

    Next a review paid by a party that does not hold the operator's keys, which the manifest would show as an external record.

  3. The sandbox is operator-owned and operator-funded

    In the sandbox, the treasury, agent, payer and vendor accounts are operator-owned and operator-funded on Hedera testnet. Visitors choose proposals under a policy signed in advance; sandbox runs are operator-run reliability exercises, not users or external usage. The allowance and funding are finite. Recent runs remain available after exhaustion. Guard authorization is reported separately from mirror-node execution evidence.

    Next an independently owned and funded treasury, with its own owner-signed policy and separately attributed evidence.

  4. The seller is ours

    The buyer-path purchase went to a seller we operate with stock x402 libraries. No external merchant sold anything and no customer bought anything.

    Next a purchase from a Hedera x402 seller we do not run.

  5. Listed in no directory

    The caller resolves the guard from a configured origin and an expected HCS-14 identifier. Nothing else can find it, and an identifier match is not cryptographic proof that the host controls the guard key.

    Next a challenge-response over the guard key at resolution time, and a listing the owner chooses.

  6. One tenant, enrolled by hand

    The code can serve several tenants, but the deployed instance serves one treasury, and every tenant is written into the guard's configuration by the operator. There is no self-enrollment endpoint. This is not a marketplace.

    Next an enrollment path the owner can complete without the operator, with its own review.

  7. HTS is refused on the schedule path

    HTS approval differs by route. On the schedule path (POST /review) every token proposal is refused, because that path does not resolve the token's consensus fee state. On the transfer path (POST /countersign) the guard resolves TokenInfo from consensus and approves a fungible token only when it carries no custom fees and an immutable fee schedule. That route is registered, paid and tested, but it has not been exercised live on testnet and no token run appears in evidence.json.

    Next exercising the transfer path's token route live on testnet so it has ledger evidence, and resolving the token's fee schedule on the schedule path too.

  8. On the schedule path the guard approves a ScheduleID, not bytes

    ScheduleSign authorizes the immutable schedule the guard resolved from consensus. The guard never signs the scheduled transaction's bytes. On the buyer path it does countersign the exact bytes it validated. The two are different guarantees and the how-it-works page keeps them apart.

    Next nothing to fix; the point is not to describe one path in the other's words.

  9. One mandate per approval

    Mandates are single-use. A treasury that makes ten transfers needs ten owner-signed mandates with increasing nonces. There is no standing allowance.

    Next a bounded multi-use mandate with a running spend counter, and its replay tests.

  10. A refusal costs the same as an approval

    The review fee settles before any consensus work and is not returned on a refusal. On 2026-09-12 the agent card quoted 1,000,000 tinybars per review. This is a design choice, since the refusal is the delivered service, but a caller should know it before paying.

    Next nothing; it is stated here and in the README so it is not a surprise.

  11. The price is exact-scheme and fixed per call

    Hedera x402 supports only the exact scheme, so the price is one known amount quoted in the 402 challenge. There is no metering, no volume pricing, and the amount is operator configuration that can change.

    Next a scheme change upstream, which this project does not control.

  12. One process on one host

    The guard runs as a single systemd service behind nginx with a file-backed SQLite database for nonce reservations. Lock contention is bounded and surfaces as a retryable 503. There is no replica, no failover and no uptime commitment.

    Next a second instance sharing reservation state without weakening single-use.

  13. A network upgrade stops all approvals

    The guard refuses every review whose consensus node reports protobuf or services versions outside its reviewed allowlist. When Hedera upgrades, the guard refuses everything until a person re-reviews the schema. Fail-closed by design, but a real outage window.

    Next a documented re-review procedure with a time bound.

  14. The verdict record is the guard's own word; the absence is not

    The HCS verdict message is written by the guard and is only as honest as the guard. What does not depend on the guard is the ledger state: an unexecuted schedule with no guard prefix, or a transaction ID the mirror node has never seen. Trust the absence; treat the record as a convenience index into it.

    Next nothing; this is the correct reading of the evidence and the evidence page is built on it.

  15. No independent security audit

    The code has been reviewed and mutation-tested internally, and the invariant-to-test map and threat model are published. No third party has audited it. The offline suite is 520 TypeScript and 13 Python tests as of 2026-09-12, and it covers the validator, not the deployment.

    Next an external review of src/review-schedule.ts, src/countersign-transfer.ts and src/payment-gate.ts against the threat model.
